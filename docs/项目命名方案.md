# PMM Studio 项目命名方案

> 状态：已定稿 · 适用范围：项目对外命名、模块划分、代码标识与文档用语
> 一句话：**PMM Studio = Product（产品）+ Media（媒体）+ Material（资料）三位一体的内容中台与创作工作台。**

---

## 1. 命名总览

项目名 `PMM Studio` 由两部分构成：

| 组成 | 含义 | 作用 |
|---|---|---|
| `PMM` | Product · Media · Material 三个词的首字母缩写 | 声明产品的三大能力模块，直接对应系统内的三块数据 |
| `Studio` | 工作室 / 创作工作台 | 声明产品的形态定位：面向"生产与整理对外内容"的工作台，而非单纯的数据库 |

缩写 `PMM` 与后缀 `Studio` 共同完成两件事：**说清管什么（三个模块），说清是什么（工作台）**。
只叫 `PMM` 会像个内部系统代号，只叫 `Studio` 又过于空泛，二者组合才既准确又可记忆。

---

## 2. 字母拆解

| 字母 | 原词 | 对应模块 | 在项目中指什么 |
|---|---|---|---|
| **P** | **Product** | 产品库 | 产品型号、参数表、规格书、分类目录、SKU 管理 |
| **M** | **Media** | 媒体资源 | 产品图片、宣传视频、3D 模型、海报、Banner 等素材资产 |
| **M** | **Material** | 内容 / 资料 | 教程文档、技术手册、安装指南、案例文章、FAQ 等内容管理 |

三个模块共享一个锚点：**以产品（P）为中心**，媒体（Media）与资料（Material）都是围绕产品组织的对外输出物。
因此数据关系上应始终是"产品关联素材 / 产品关联文档"，而不是三套互不相干的独立库。

---

## 3. 为什么是这三个模块

产品的核心诉求是「把产品的对外表达统一管起来」，而对外表达恰好只需要三类东西：

1. **说清产品本身** —— 型号、参数、规格、SKU → `Product`
2. **让人看见产品** —— 图、视频、3D、海报 → `Media`
3. **让人会用产品** —— 教程、手册、指南、FAQ → `Material`

三者覆盖了从「是什么」到「看得见」再到「用得会」的完整链路，缺一块则内容生产链条断裂：

- 缺 P：素材和文档失去归属，退化为网盘式堆叠；
- 缺 Media：产品只有文字参数，不具备营销与展示能力；
- 缺 Material：产品只有卖点，没有售后与上手支撑。

---

## 4. `Studio` 后缀的含义

`Studio` 不是装饰词，它约束了产品形态：

| 隐含语义 | 对产品的约束 |
|---|---|
| 工作台 / 生产场所 | 强调**产出**：能在这里加工出可直接对外发布的物料，而不只是存档 |
| 素材工作室 | 强调**组织方式**：按项目、产品、渠道聚合素材，支持复用与批量处理 |
| 创作感 / 轻专业工具 | 强调**体验基调**：面向运营与市场人员，操作门槛低于传统 PIM / DAM |

对比更常见的后缀：`Hub` 偏汇聚（只进不出）、`Center` 偏管理后台（重管控）、`Base` 偏数据库（重存储）。
`Studio` 是本项目唯一同时表达「管理 + 生产 + 对外输出」的词。

---

## 5. 模块边界判定规则

缩写里有两个 `M`，实际落地时最容易混，必须给出可执行的判定标准。

### 5.1 Media 与 Material 的分界

| 维度 | Media（媒体资源） | Material（内容 / 资料） |
|---|---|---|
| 载体 | 二进制文件本身 | 有结构的文本内容 |
| 典型消费方式 | 预览、播放、放大查看 | 阅读、检索、按章节浏览 |
| 组织形式 | 文件夹 / 标签 / 集合 | 目录 / 章节 / 版本 |
| 生命周期 | 会被替换、重出图、追新版 | 会被修订、增补、废弃 |
| 判断口诀 | **有查看器/播放器的归 Media** | **有阅读页/目录的归 Material** |

### 5.2 交叉情形的归属

| 情形 | 归属 | 说明 |
|---|---|---|
| 安装视频教程 | 视频文件 → `Media`；教程正文与步骤 → `Material` | 两边各存一份职责，`Material` 引用 `Media` 资源 ID，不重复上传 |
| 产品海报 | 海报图 → `Media` | 海报上的营销文案若需单独维护，作为该素材的描述字段，不另建文档 |
| 产品规格书 PDF | 文件 → `Media`；结构化参数 → `Product` | 参数以字段形式沉淀在 `Product`，PDF 仅作原始凭证留存 |
| FAQ 单条问答 | `Material` | 即使短小，只要是可阅读内容就归资料 |
| 3D 模型 | `Media` | 属于可视化资产，不承载阅读语义 |
| Banner 图 + 跳转链接 | `Media` | 链接是可配置属性，不构成独立模块 |

### 5.3 新增功能归属自检

新增一个能力前，先回答：

1. 它描述的是**产品本身的属性**吗？→ `Product`
2. 它的主要形态是**文件且需要预览/播放**吗？→ `Media`
3. 它的主要形态是**文字且需要被阅读/检索**吗？→ `Material`
4. 三个都不是 → 它很可能是**支撑能力**（权限、检索、发布、日志），不应塞进三个模块，而是作为公共层处理。

## 6. 命名延展规范

缩写一旦确定，就应在代码、数据、界面三层保持一致，避免同一概念多种叫法。

### 6.1 书写规范

| 场景 | 正确 | 错误 |
|---|---|---|
| 正式项目名 | `PMM Studio` | PMMStudio、PMM studio、pmm Studio |
| 缩写单独使用 | `PMM` | P.M.M、pmm（作为产品名时） |
| 小写标识 | `pmm`、`pmm-studio` | pmm_studio（包名/仓名场景） |
| 模块名 | `Product` / `Media` / `Material` | Production、Multimedia、Materials |

> 中文语境下直接沿用 `PMM Studio`，不做逐字翻译（如"产品媒体资料工作室"），以保持品牌一致性。

### 6.2 代码与数据标识

| 层 | 约定 | 示例 |
|---|---|---|
| 包 / 仓库 | `pmm-studio`，子包 `@pmm/<module>` | `@pmm/ui`、`@pmm/product` |
| 模块目录 | 单数小写 | `src/modules/product`、`media`、`material` |
| 数据表 / 集合 | 复数小写，必要时加前缀 | `products`、`media_assets`、`materials` |
| 路由 | 复数小写 | `/products`、`/media`、`/materials` |
| 对外 API 前缀 | `/api/v1/<resource>` | `/api/v1/products` |
| 环境变量 | 大写下划线 | `PMM_*` |

> 模块目录用单数、表与路由用复数：前者表示"某模块"，后者表示"某类资源集合"，语义各自清楚。

### 6.3 界面文案

- 导航一级菜单使用中文全称：**产品库 / 媒体资源 / 内容资料**，与缩写一一对应；
- 需要露出英文时使用 `Product` / `Media` / `Material`，不与中文混写成"产品 Product 库"；
- 首页或关于页固定呈现一句定位语（见第 7 节），不各页自行发挥。

## 8. 备选方案与取舍

命名时考虑过更常见的行业缩写，均因覆盖不全或歧义而被排除：

| 备选 | 含义 | 未采用原因 |
|---|---|---|
| `PIM` | Product Information Management | 只覆盖产品信息，Media 与 Material 无处安放，语义偏后端主数据 |
| `DAM` | Digital Asset Management | 只覆盖媒体资产，缺产品库与文档内容，且偏"存档"而非"创作" |
| `CMS` | Content Management System | 已被泛化，几乎任何后台都可自称 CMS，缺乏辨识度与边界 |
| `PLM` | Product Lifecycle Management | 已有明确行业含义（研发/生命周期流程），与本项目定位冲突 |
| `PMS` | —— | 极易被理解为 Project Management System，歧义最大 |
| `PMC` | —— | 与"生产计划与物料控制"行业术语撞车 |

`PMM` 的优势在于：三个字母都是**内容域名词**，无既有强绑定含义，且首字母组合后仍可读、可记、可检索。

## 9. 术语表

| 术语 | 定义 |
|---|---|
| PMM | Product · Media · Material 的缩写，同时指代本系统的三大模块 |
| Product（产品） | 一个可对外销售的型号/系列，拥有参数、规格、分类与 SKU |
| Media（媒体） | 可预览的视觉类资产文件，如图片、视频、3D 模型 |
| Material（资料） | 面向阅读与检索的文档型内容，如教程、手册、FAQ |
| 素材 | 口语层面对 Media 与 Material 的统称，正式文档中应避免单独使用 |
| 工作台 | 支持"整理 → 加工 → 对外输出"全流程的操作界面，区别于纯管理列表页 |

- [ ] 命名在代码、数据、路由、界面四处一致（第 6 节）
- [ ] 与其他模块的关联以产品为中心，未产生重复存储

- [ ] 未把支撑能力（权限、检索、发布）包装成第四个业务模块
