# PMM Studio 技术选型方案

> 状态：**已确认** · 依据：2026-10-28 需求澄清（5 轮问答）
> 结论：**自研 Next.js 全栈单体，Prisma + PostgreSQL，本地磁盘存储，Docker Compose 部署在美国 VPS。**
> 规模：**2 个账号，40 GB 磁盘，5 GB/人 配额（含本地视频），后台简体中文 / 公开页台湾繁体，视频支持本地 + YouTube 双通道。**

---

## 1. 已确认的需求约束

| 维度 | 结论 | 对架构的硬性影响 |
|---|---|---|
| 部署 | 美国 VPS，自托管 | 不能依赖 Vercel / 云托管函数；需要 Docker 与自动化 HTTPS |
| 账号 | **2 个账号，一人一号，永不支持团队** | 每张业务表带 `account_id`，服务端强制过滤；**不需要**组织 / 成员 / 角色表 |
| 数据隔离 | 每个账号只管自己的产品 / 媒体 / 资料 | 所有查询必须带账号作用域，不能出现跨账号串数据 |
| 对外展示 | 每个账号一个公开链接，给客户看 | 免登录只读路由 + 内容「是否公开」开关 |
| 链接形态 | 路径式 `/s/<slug>` | 一张普通证书即可，不需要泛域名证书 |
| 开通方式 | 管理员手动创建 | 不做自助注册、邮箱验证、找回密码 |
| 前端 | React / Next.js | 技术栈锁定 React 生态 |
| 磁盘 | **仅 40 GB** | 存储预算而非"够不够"是首要约束；视频必须限时长与码率 |
| 配额 | **5 GB/人**（合计 10 GB），硬上限 8 GB/人 | 图片与**本地视频**共同计入配额，需要按类型统计占用 |
| 媒体 | 图片为主，本地磁盘 | 需要存储抽象层，为将来切对象存储留口 |
| 视频 | **首期双通道：本地存储 + YouTube 外链** | 本地视频走转码管线并计入配额；外链走 iframe 嵌入 |
| 语言 | 后台**简体中文**，公开页**繁体中文（台湾）** | 内容字段双语存储 + UI 字典两套 |
| 简繁转换 | **OpenCC `twp`（台湾正体 + 词汇转换）** | 自动转换 + 人工校对，型号与 slug 禁止转换 |
| 公开页功能 | **一期只做展示，不做表单/埋点** | 不收集任何个人信息，规避 GDPR / CCPA 合规成本 |
| 客户地域 | 台湾为主 | 公开页用词按台湾习惯，需维护术语对照表 |
| 后台访问 | 有本地高速代理节点 | 跨境延迟不影响后台体验；无需为管理端做特殊优化 |
| 初始数据 | 从零录入 | 一期不做导入器 |

### 四条影响选型的推论

1. **"一人一号且永不支持团队"把多租户彻底简化了。** 不需要组织 / 成员 / 角色三层，只要一个 `account_id` 贯穿所有表，隔离逻辑在服务端集中实现，不需要租户路由、租户独立库或 RLS 平台。
2. **公开展示页是产品的脸面，不是附属功能。** 客户看到的就是 `/s/<slug>` 这个页面，它决定了视觉定制需求很高——模板化方案的短板正好落在这里。
3. **单台 VPS 意味着运维预算很低。** 每多一个中间件（Redis、搜索服务、消息队列、独立 CMS）就多一份内存占用、升级负担和故障面。
4. **40 GB 磁盘 + 2 人规模，让"要不要引入云服务"的答案变成"不要"。** 对象存储、CDN、托管数据库在 10 GB 量级都是负收益：多一层配置、多一处凭据、多一个故障点。

## 2. 方案对比

四套可行路径，按「自研程度」从高到低排列。

### 2.1 对比表

| 维度 | **A. 自研 Next.js 全栈** | **B. NocoBase 低代码** | **C. Directus 无头 CMS + 前端** | **D. Supabase(BaaS) + 前端** |
|---|---|---|---|---|
| 首版可用工期 | 3–4 周 | 1–1.5 周 | 2–3 周 | 2–3 周 |
| 账号数据隔离 | 自己写，逻辑集中、最好理解 | 内置角色与数据范围，但按账号逐表配置繁琐 | 内置 roles + 权限过滤，表达能力中等 | RLS 原生支持，隔离最"正统" |
| 公开展示页 | 完全可控（SSR、OG 图、动效） | 分享页模板化，视觉受限 | 需另写前端，可控 | 需另写前端，可控 |
| 图片多尺寸 / 3D | 全可控（sharp、`<model-viewer>`） | 弱，需插件补 | 中，自带变换但 3D 要自研 | 中，自带变换但 3D 要自研 |
| 简繁双语内容 | 自己建双列，转换流程可定制 | 平台无简繁流程，需二次开发 | 需自建 i18n 结构 | 需自建 i18n 结构 |
| 文档编辑体验 | 自选编辑器，体验可打磨 | 内置富文本，样式普通 | Markdown 内置，够用 | 自研 |
| 单 VPS 运维 | 低（1 app + 1 DB） | 中（Node + DB + Redis） | 中高（CMS + 前端 + DB） | 高（自托管整套服务） |
| 定制上限 | 无上限 | 受平台边界约束 | 受 CMS 模型约束 | 较高 |
| 供应商锁定 | 低 | **高**（平台 DSL 与插件体系） | 中 | 中高（BaaS API 与鉴权体系） |
| 长期维护 | 中（自己负责升级） | 低（平台统一升级） | 中 | 中高 |

### 2.2 取舍说明

- **B（NocoBase）** 在「一周内出可点系统」上优势最大，但核心价值在 `/s/<slug>` 那个对外页面——它需要品牌级视觉，低代码分享页很难做到位；同时锁定风险最高，未来想改交互基本等于重写。
- **C（Directus）** 内容建模适合 Material 模块，但 Product 的参数表与 Media 处理链路仍需大量自定义，最后演变成「CMS 只做后台、业务在两个系统里」，比自研更绕。
- **D（Supabase）** 的 RLS 是最优雅的隔离机制，但要跑在自己的 VPS 上就得自托管一整套（Postgres + GoTrue + PostgREST + Realtime + Studio），内存与升级成本对单机不划算；用托管版又违背「部署在自己的 VPS」。
- **A（自研）** 唯一劣势是工期，但「一人一号」把复杂度削掉一大半，且三个模块界面形态差异大（参数表格、素材画廊、文档阅读），自研才有统一交互语言。

> **结论：选 A。** 理由不是"自研更高级"，而是这套需求里最难的部分（对外页面体验 + 媒体处理 + 简繁转换 + 单机低运维）恰好是低代码与 BaaS 的弱项，而它们的强项（内置权限、内置表单）在简化模型下收益有限。

## 3. 技术栈明细

| 层 | 选型 | 理由 |
|---|---|---|
| 运行时 | Node.js 22 LTS | 与 Next.js 15 匹配，长期支持 |
| 框架 | **Next.js 15（App Router + RSC）** | 一套代码同时产出后台与公开页，SSR 对展示页 SEO/OG 友好 |
| 语言 | TypeScript 5（strict） | 三模块共用类型，字段改动能编译期暴露 |
| UI | Tailwind CSS v4 + shadcn/ui + lucide-react | 视觉可深度定制，组件拷入源码，无运行时锁定 |
| 数据库 | **PostgreSQL 16** | JSONB 存产品参数、全文检索、事务够用，单机资源占用低 |
| ORM | **Prisma** + Prisma Migrate | 用户指定；迁移工具成熟，`$extends` 可集中实现账号作用域 |
| 鉴权 | Auth.js v5（Credentials）+ argon2 | 手动建号场景只需账号密码 |
| 校验 | Zod | 前后端共用 schema，表单/接口同一份规则 |
| 表单 | react-hook-form + Zod resolver | 参数表这类长表单体验最好 |
| 富文本 | **TipTap**（ProseMirror） | 面向非技术运营，Markdown 编辑器对他们是负担 |
| 简繁转换 | **opencc-js**（`cn → twp`） | 纯 JS 无原生依赖，支持台湾正体 + 词汇转换 |
| 图片处理 | sharp | 生成主图 + 多档衍生，上传即处理 |
| 视频处理 | **ffmpeg**（Docker 内安装） | 统一转 720p H.264 + faststart，抽首帧做封面 |
| 视频（本地） | 自托管 MP4，经 Caddy 静态服务 | 无品牌痕迹、无第三方依赖；支持 Range 拖动 |
| 视频（外链） | **YouTube / Vimeo iframe**（`youtube-nocookie`） | 长视频零存储成本，台湾有本地 CDN 节点 |
| 3D 预览 | `<model-viewer>` | Web Component，无需引入完整 three.js 场景管理 |
| 搜索 | PostgreSQL `tsvector` + `pg_trgm`（仅简体列） | 数据量级不需要 Elasticsearch；公开页不搜索，索引只需一套 |
| 包管理 | pnpm | 单 VPS 上安装快、磁盘占用小 |
| 部署 | **Docker Compose（app + postgres + caddy）** | Caddy 自动签发 Let's Encrypt 证书 |
| 日志 | pino（结构化 JSON）+ docker log rotation | 单机场景容器日志轮转即可 |
| 备份 | `pg_dump` 每日 + 上传目录 rsync 异地 | 单 VPS 没有冗余，备份是唯一安全网 |

### 刻意不引入的东西

| 未引入 | 原因 | 何时再加 |
|---|---|---|
| Redis | 无会话共享、无缓存热点、无队列强需求 | 出现后台任务积压或接口变慢时 |
| 独立搜索引擎 | 内容量级在万行以内，且公开页不搜索 | 相关性明显不足时 |
| 对象存储 | 总量封顶 16 GB，本地盘够用 | 上传目录超 20 GB 或需要多机时 |
| 消息队列 | 单文件 ≤ 200 MB，转码在请求内 1–2 分钟可完成，用 `status` 字段兜住即可 | 出现批量导入或并发转码排队时 |
| Monorepo | 只有一个应用，拆包只增负担 | 出现第二个可独立部署的服务时 |
| next-intl 等 i18n 框架 | 只有两种语言且公开页单语 | 需要第三种语言时 |
| Stripe 计费 | 无收费需求 | 明确要卖订阅时 |

### 3.1 Prisma 的两处部署要求

1. **镜像内引擎**：用 `output: 'standalone'` 打包时须显式声明 `binaryTargets`（如 `["native", "debian-openssl-3.0.x"]`），否则容器内启动报引擎缺失。
2. **迁移执行**：生产环境在容器启动时执行 `prisma migrate deploy`，开发环境用 `migrate dev`；迁移文件必须入库，不允许用 `db push` 上生产。

## 4. 关键设计

### 4.1 数据模型

```text
accounts      id / email / password_hash / slug / display_name / status
              storage_quota_bytes(默认 5 GiB) / storage_used_bytes / created_at

categories    id / account_id / name_hans / name_hant / sort

spec_fields   id / account_id / key(ascii) / label_hans / label_hant / unit / type / sort
              ← 参数字典（"内存"/"記憶體"这类表头双语）

products      id / account_id / category_id / name_hans / name_hant
              model_no(禁止转换) / specs(jsonb) / is_public / sort / hant_reviewed

media_assets  id / account_id / product_id?
              kind ← image | video_local | video_external | model_3d
              provider(youtube|vimeo) / external_id      ← 外链时使用
              storage_key / bytes / width / height        ← 本地时使用
              duration_sec / poster_key(必填) / variants(jsonb)
              status ← processing | ready | failed
              is_public / created_at

materials     id / account_id / product_id? / title_hans / title_hant / slug(禁止转换)
              content_hans / content_hant / is_public / hant_reviewed / sort
```

约定：

- `account_id` 出现在**每一张业务表**（`accounts` 除外），即使能通过 `product_id` 间接推导也不省——它让每个查询独立完成隔离，不依赖 JOIN 链路。
- `is_public` 决定是否出现在 `/s/<slug>`，默认 `false`，必须显式勾选。
- `slug` 全局唯一，用拼音或随机串，**不用中文**，避免 URL 编码与转换问题。
- 表名复数小写下划线（`media_assets`），Prisma 模型单数 PascalCase + `@@map`。
- 视频的 `poster_key` **必填**：没有封面时公开页会先出现空白块，且无法生成 OG 分享图。

### 4.2 账号隔离执行策略

| 层 | 做法 |
|---|---|
| 数据访问 | 唯一出口是封装后的 `db`：Prisma Client Extension 在 `$allModels.$allOperations` 中从 AsyncLocalStorage 取 `accountId` 注入 `where` |
| 白名单 | `accounts` 与管理员路由不走作用域，其余模型全部强制 |
| **禁止裸 SQL** | `$queryRaw` / `$executeRaw` 扩展拦不住，**全面禁用**；确需时集中到一个显式豁免的白名单文件 |
| 写入 | 服务端从会话取 `accountId` 覆盖请求体同名字段，**永不信任客户端传的 account_id** |
| 静态约束 | ESLint 禁止 `src/app` 直接 import `@prisma/client`，只能 import `@/lib/db` |
| 公开路由 | `/s/<slug>` 只走只读查询，额外强制 `is_public = true` |
| 越权语义 | 用 A 账号会话请求 B 账号资源，返回 **404 而非 403**，不泄露资源存在性 |
| 测试 | 跨账号越权测试进 CI，新增模型必须补一条 |

### 4.3 公开页设计

```text
/s/<slug>              账号主页：分类 + 产品卡片 + 资料入口
/s/<slug>/p/<model>    产品详情：参数表 + 媒体画廊 + 关联资料
/s/<slug>/m/<slug>     资料阅读页
```

- **语言**：全部输出繁体（台湾正体 + twp 词汇），用词按台湾习惯；
- **形态**：一期纯展示，无表单、无埋点、无第三方脚本，因此不涉及 GDPR / CCPA 的告知与同意；
- **渲染**：全部 SSR，带 `og:image`（`next/og` 按产品图动态生成），客户分享到 Line / Facebook 时有预览；
- **独立布局**：与后台视觉解耦，不出现后台导航；
- **未公开内容**：直接 404，不出现"该内容未公开"这类提示；
- **子域名预留**：路由层从 `slug` 解析，将来换 `Host` 解析不改数据模型。

### 4.4 配额与存储治理

40 GB 磁盘的预算是硬约束，必须写死。

| 用途 | 预算 |
|---|---|
| 系统 + Docker 引擎 | 4 GB |
| 应用镜像（含回滚保留 2 版 + 构建缓存） | 3 GB |
| PostgreSQL（数据 + WAL + dump） | 3 GB |
| 日志（含轮转） | 1 GB |
| 临时文件 / swap | 1 GB |
| **固定开销小计** | **12 GB** |
| 上传目录上限 | **≤ 22 GB** |
| 必须留的安全空余（15%） | 6 GB |
| **可分配配额总量** | **10–16 GB** |

对应到 2 个账号：

| 方案 | 合计 | 剩余空余 | 评价 |
|---|---|---|---|
| 5 GB/人（**采用**） | 10 GB | 15 GB | 空余充足，够用很久 |
| 8 GB/人（硬上限） | 16 GB | 9 GB | 可接受，接近上限 |
| 10 GB/人 | 20 GB | 5 GB | 偏危险，一个日志失控就翻车 |

**不同内容的配额消耗**（本地视频与图片共用同一个 5 GB）：

| 内容类型 | 单件占用 | 5 GB 可容纳 |
|---|---|---|
| 产品图（主图 + 三档衍生） | ≈ 2 MB | 约 2500 张 |
| 本地视频 720p H.264 | ≈ 15 MB / 分钟 | 约 340 分钟 |
| **单文件上限** | 图片 20 MB / 视频 200 MB / 时长 10 分钟 | 超限直接拒绝 |

典型混合场景：1500 张产品图（约 3 GB）+ 130 分钟本地视频（约 2 GB）= 配额用满。这意味着**视频是配额的消耗主力**，UI 必须按类型分别显示占用，否则用户会莫名其妙被拦。

执行规则：

1. **默认 5 GiB/人**，配额存 `accounts.storage_quota_bytes`，可上调不可轻易下调（下调会伤已有数据）。
2. **图片管线**：主图压到长边 3000px JPEG q82，衍生 1600 / 800 / 320 三档 WebP；**不保留原始 RAW/超大原图**。单张综合占用约 2 MB，5 GB ≈ 2500 张。
   > P1 实现时取消了 AVIF：sharp 编码 AVIF 在 2 vCPU 上单张 1–3 秒，会明显拖慢上传，体积收益有限；需要时再开。
3. **衍生图计入配额**：按磁盘真实占用计，否则 10 GB 会悄悄变成 15 GB。
4. **应用层硬上限 20 GB**：即使配额被调高也不能打满磁盘；配额保护用户，硬上限保护服务器。
5. **上传前置校验**：`used + fileSize > quota` 直接拒绝并提示剩余空间；写入前先校验磁盘水位。
6. **计数对账**：每周跑一次 `scripts/reconcile-storage.ts`，遍历上传目录 `fs.stat` 累加，与 `storage_used_bytes` 比对修正，兜住中断与删除失败造成的漂移。
7. **水位告警**：磁盘 ≥70% 告警，≥85% 拒绝新上传并通知管理员。**磁盘满会连带 PostgreSQL 故障**，这 15% 不是余量而是保险。
8. **备份出机**：`data/` 与 `pg_dump` 每日 rsync 到 VPS 之外（另一台机器或对象存储冷备），保留 7 天。

### 4.5 简繁双语内容模型

客户只看繁体，操作者只写简体，中间靠自动转换 + 人工校对。

**存储：双列，不用翻译表。** 只有两种语言、两个用户，独立 `translations` 表属于过度设计；双列能直接建索引、排序、`ILIKE` 检索，JSONB 在这些场景会别扭。

**转换流程：**

```text
后台录入简体
   ↓ 保存时 opencc-js 转换（cn → twp）
自动填充 hant 列，hant_reviewed = false
   ↓ 校对界面人工核对
hant_reviewed = true，此后自动转换不再覆盖
```

**转换范围控制（关键）：**

| 处理 | 字段 |
|---|---|
| 参与转换 | `name_hans`、`title_hans`、`content_hans`、`label_hans`、分类名 |
| **禁止转换** | `model_no`、`slug`、`spec_fields.key`、URL、代码块（`<pre>` / `<code>`） |

型号里的中文字被误转会改变含义（"大发"→"大發"），这类字段必须在管线中显式跳过。

**HTML 正文转换**：只处理文本节点，保留标签结构，跳过 `<code>`、`<pre>`、`href`、`src`、`alt` 之外的属性。

**UI 文案**：两份 TS 字典文件（`zh-Hans` / `zh-Hant`），不引入 i18n 框架。

**校对基线术语表**（台湾用语，供校对与人工补词参考）：

### 4.6 视频双通道设计

两类视频共存，入库时用 `kind` 区分，公开页统一渲染为播放器。

| | 本地视频 `video_local` | 外链视频 `video_external` |
|---|---|---|
| 适用 | 15 秒–3 分钟的短片、产品细节循环 | 3 分钟以上的演示、安装教程 |
| 存储 | 自托管，**计入配额** | 只存 `external_id`，不占磁盘 |
| 品牌痕迹 | 无 | 有 YouTube logo 与结束推荐位 |
| 播放体验 | 跨太平洋，起播 1–3 秒 | 台湾本地 CDN，基本秒开 |
| 依赖 | 无 | YouTube 政策与账号可用性 |

**本地视频上传管线（必须标准化，不能透传原文件）：**

```text
上传 → 校验大小/时长 → 落临时文件，status = processing
  → ffmpeg -i in.mov -vf scale=-2:720 -c:v libx264 -crf 23
           -preset veryfast -movflags +faststart -c:a aac -b:a 128k out.mp4
  → 抽首帧生成 poster.jpg（长边 1600）
  → 写入 bytes / duration_sec，status = ready，累加配额
```

三条理由：

1. **格式兼容**：iPhone 默认 HEVC/.MOV，Chrome 与 Firefox 无法播放。透传必然出现「视频打不开」。
2. **体积可控**：4K 素材原样入库会瞬间击穿配额，转 720p 后约 15 MB/分钟。
3. **`+faststart`**：把索引挪到文件头，否则浏览器要下完整个文件才能起播。

**决定：一次性标准化，不做实时流式转码。** 2 个账号的量级下，单文件 ≤ 200 MB / 10 分钟，2 vCPU 转码约 1–2 分钟，用 `status = processing` 兜住即可，不引入队列服务。

> 若不想引入 ffmpeg，可退化为「只接受 H.264 MP4，其余拒绝」：省一条管线，但用户得自己转码，实际会频繁踩坑，不推荐。

**播放路径：由 Caddy 直接服务，不经 Next.js。**

```caddyfile
handle_path /media/* {
    root * /srv/data/uploads
    file_server
    header Cache-Control "public, max-age=31536000, immutable"
}
```

`file_server` 自带 Range（206）、ETag 与零拷贝，拖动进度条无需自己实现；走 Next.js Route Handler 要手写 Range 解析，还会占用 Node 单线程。

**访问控制**：文件名用 ULID（不可猜测），公开页只引用 `is_public = true` 的资源。产品素材非机密数据，不可猜路径 + 公开开关足够；将来若要严格鉴权再改签名 URL。

**外链视频渲染**：用「封面图 + 点击加载」的 facade，避免首屏加载几百 KB 的 iframe，也避免用户未点击就产生第三方 cookie。

```tsx
// 点击后才挂载 iframe
<button onClick={load}>
  <Image src={poster} alt={title} fill />
</button>
```

## 6. 部署拓扑

```text
                 ┌──────────── Caddy（自动 HTTPS）────────────┐
  Internet ──443──▶                                          │
                 └──┬──────────────────────────────┬──────────┘
                    │                              │
              ┌─────▼─────┐                  ┌─────▼─────┐
              │ Next.js   │──┬──────────────▶│PostgreSQL │
              │ (app)     │  │               └───────────┘
              └───────────┘  │               ┌───────────┐
                    │        └──────────────▶│ ./data    │
                    └── 只读挂载上传目录 ◀────│ (volume)  │
                                             └───────────┘
```

VPS 规格：

| 项 | 建议 | 依据 |
|---|---|---|
| CPU | 2 vCPU | sharp 处理大图是 CPU 密集，2 人并发上传概率低 |
| 内存 | 4 GB | Next.js ~400 MB + Postgres ~300 MB + Caddy ~20 MB |
| 磁盘 | **现有 40 GB 可用，无需扩容** | 固定开销 12 GB + 配额 10 GB + 空余 15 GB |
| 备份 | 异地异机 | 本机备份和单点故障是同一个故障 |

关键配置：

- Next.js 用 `output: 'standalone'`；
- **镜像内安装 ffmpeg**（alpine 约 +80 MB），否则视频管线无法运行；
- 上传目录挂载为 volume，**不放在容器内**，否则重建即丢；Caddy 需只读挂载同一 volume 才能服务 `/media/*`；
- 数据库不暴露公网端口，仅容器网络内可达；
- docker 日志开 `max-size`，否则日志会吃掉磁盘预算。

## 8. 风险

| 风险 | 等级 | 影响 | 应对 |
|---|---|---|---|
| **磁盘水位** | 高 | 40 GB 盘，磁盘满会连带 PostgreSQL 故障，可能损坏数据 | 配额 5 GB + 硬上限 20 GB + 70%/85% 两级告警 + 日志轮转 + 不保留原始大图 |
| **繁简转换质量** | 中高 | 自动转换错误会直接暴露给台湾客户，影响专业度 | 型号/slug 禁转、强制人工校对、`hant_reviewed` 状态位、维护术语基线表 |
| **跨账号越权** | 高 | 数据泄露是致命事故 | Prisma Extension 统一注入 + 禁用裸 SQL + ESLint 约束 + 越权测试进 CI |
| **视频格式兼容** | 中高 | iPhone 默认 HEVC/.MOV，Chrome 与 Firefox 无法播放 | ffmpeg 统一转 720p H.264 + faststart，原文件不透传 |
| **磁盘被视频吃掉** | 中高 | 视频每分钟占用是图片的 7 倍以上，容易在用户无感知下顶满配额 | 单文件 200 MB / 10 分钟上限、UI 按类型显示占用、超 70% 提示 |
| 单点故障 | 中 | 单 VPS 无冗余，宕机即全站不可用 | 每日异地备份 + 快照；不承诺高可用 |
| 台湾用语覆盖不全 | 中 | `twp` 词库有限，部分行业术语仍会转错 | 术语基线表持续补充，校对人可编辑 |
| 图片处理 CPU 峰值 | 低 | 大批量上传时响应变慢 | 单张处理走同步管线，批量上限限制 |

> 关于跨境延迟：客户在台湾访问美国 VPS 属于可接受范围，后台有本地代理节点，**后台体验已不是风险**。唯一的例外是自托管视频——跨太平洋拉流起播约 1–3 秒，Caddy 的 Range 支持保证可拖动；若追求秒开，长视频改走 YouTube 外链即可。公开页若需更快首屏，可加 Cloudflare 缓存，非必需。
