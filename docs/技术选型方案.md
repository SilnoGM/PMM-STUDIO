# PMM Studio 技术选型方案

> 状态：待确认 · 依据：2026-10-28 需求澄清（3 轮问答）
> 结论摘要：**推荐方案 A —— 自研 Next.js 全栈单体，PostgreSQL + 本地存储起步，Docker Compose 部署在美国 VPS。**

---

## 1. 已确认的需求约束

| 维度 | 结论 | 对架构的硬性影响 |
|---|---|---|
| 部署 | 美国 VPS，自托管 | 不能依赖 Vercel / 云托管函数；需要 Docker 与自动化 HTTPS |
| 账号 | 多账号，**一人一号** | 每张业务表都要有 `account_id`，服务端强制过滤 |
| 数据隔离 | 每个账号只管自己的产品 / 媒体 / 资料 | 所有查询必须带账号作用域，不能出现跨账号串数据 |
| 对外展示 | 每个账号一个公开链接，给客户看 | 需要一条**免登录只读路由** + 内容「是否公开」开关 |
| 链接形态 | 路径式 `/s/<slug>` | 一张普通证书即可，暂不需要泛域名证书 |
| 开通方式 | 管理员手动创建 | 不做自助注册、邮箱验证、找回密码流程 |
| 前端 | React / Next.js | 技术栈已锁定 React 生态 |
| 媒体 | 图片为主，先用本地磁盘 | 需要存储抽象层，为将来切对象存储留口 |
| 初始数据 | 从零录入 | 一期不做导入器 |

### 三条最影响选型的推论

1. **"一人一号"让多租户变简单了。** 不需要组织 / 成员 / 角色三层，只要一个 `account_id` 贯穿所有表，隔离逻辑在服务端集中实现即可，不需要引入租户路由、租户库或 RLS 平台。
2. **公开展示页是产品的脸面，不是附属功能。** 客户看到的就是 `/s/<slug>` 这个页面，它决定了视觉定制需求很高——模板化方案的短板正好落在这里。
3. **单台 VPS 意味着运维预算很低。** 每多一个中间件（Redis、搜索服务、消息队列、独立 CMS）就多一份内存占用、升级负担和故障面。

## 2. 方案对比

四套可行路径，按「自研程度」从高到低排列。

### 2.1 对比表

| 维度 | **A. 自研 Next.js 全栈** | **B. NocoBase 低代码** | **C. Directus 无头 CMS + 前端** | **D. Supabase(BaaS) + 前端** |
|---|---|---|---|---|
| 首版可用工期 | 3–4 周 | 1–1.5 周 | 2–3 周 | 2–3 周 |
| 账号数据隔离 | 自己写，逻辑集中、最好理解 | 内置角色与数据范围，但按账号逐表配置繁琐 | 内置 roles + 权限过滤，表达能力中等 | RLS 原生支持，隔离最"正统" |
| 公开展示页 | 完全可控（SSR、OG 图、动效） | 分享页模板化，视觉受限 | 需另写前端，可控 | 需另写前端，可控 |
| 图片多尺寸 / 3D / 视频 | 全可控（sharp、`<model-viewer>`） | 弱，需插件补 | 中，自带变换但 3D 要自研 | 中，自带变换但 3D 要自研 |
| 文档编辑体验 | 自选编辑器，体验可打磨 | 内置富文本，样式普通 | Markdown 内置，够用 | 自研 |
| 单 VPS 运维 | 低（1 app + 1 DB） | 中（Node + DB + Redis） | 中高（CMS + 前端 + DB） | 高（自托管整套服务） |
| 定制上限 | 无上限 | 受平台边界约束 | 受 CMS 模型约束 | 较高 |
| 供应商锁定 | 低 | **高**（平台 DSL 与插件体系） | 中 | 中高（BaaS API 与鉴权体系） |
| 长期维护 | 中（自己负责升级） | 低（平台统一升级） | 中 | 中高 |

### 2.2 取舍说明

- **B（NocoBase）** 在「一周内出可点系统」上优势最大，但你的核心价值在 `/s/<slug>` 那个对外页面——它需要品牌级视觉与响应式排版，低代码的分享页很难做到位；同时锁定风险最高，未来想改交互基本等于重写。
- **C（Directus）** 的内容建模能力很适合 Material 模块，但 Product 的参数表与 Media 的处理链路仍需大量自定义，最后会演变成「CMS 只做后台，业务全在两个系统里」，反而比自研更绕。
- **D（Supabase）** 的 RLS 是这个需求下最优雅的隔离机制，但要跑在美国 VPS 上就得自托管一整套（Postgres + GoTrue + PostgREST + Realtime + Studio），内存与升级成本对单机不划算；若改用托管版，则违背「部署在自己的 VPS」这一条。
- **A（自研）** 唯一劣势是工期最长，但「一人一号」这个约束把多租户的复杂度削掉了一大半，实际工作量比想象中小。且三个模块的界面形态差异大（参数表格、素材画廊、文档阅读），自研才有统一的交互语言。

> **结论：选 A。** 理由不是"自研更高级"，而是这套需求里最难的部分（对外页面体验 + 媒体处理 + 单机低运维）恰好是低代码与 BaaS 的弱项，而它们的强项（内置权限、内置表单）在你的简化模型下收益有限。

## 3. 推荐技术栈明细

| 层 | 选型 | 理由 |
|---|---|---|
| 运行时 | Node.js 22 LTS | 与 Next.js 15 匹配，长期支持 |
| 框架 | **Next.js 15（App Router + RSC）** | 一支代码同时产出后台与公开页，SSR 对展示页 SEO/OG 友好 |
| 语言 | TypeScript 5（strict） | 三模块共用类型，字段改动能在编译期暴露 |
| UI | Tailwind CSS v4 + shadcn/ui + lucide-react | 视觉可深度定制，组件按需拷入源码，无运行时锁定 |
| 数据库 | **PostgreSQL 16** | JSONB 存产品参数、全文检索、事务都够用，单机资源占用低 |
| ORM | **Drizzle ORM** + drizzle-kit | SQL 显式、bundle 小、事务直观；便于统一注入 `account_id` 作用域 |
| 鉴权 | Auth.js v5（Credentials）+ argon2 | 手动建号场景只需账号密码，无需第三方登录 |
| 校验 | Zod | 前后端共用 schema，导入/表单/接口同一份规则 |
| 表单 | react-hook-form + Zod resolver | 参数表这类长表单体验最好 |
| 富文本 | **TipTap**（ProseMirror） | 面向非技术运营，Markdown 编辑器对他们是负担 |
| 图片处理 | sharp | 生成 3 档尺寸 + WebP/AVIF，上传即处理 |
| 3D 预览 | `<model-viewer>` | Web Component，无需引入完整 three.js 场景管理 |
| 搜索 | PostgreSQL `tsvector` + `pg_trgm` | 数据量级不需要 Elasticsearch，少一个服务少一份内存 |
| 包管理 | pnpm | 单 VPS 上安装快、磁盘占用小 |
| 部署 | **Docker Compose（app + postgres + caddy）** | Caddy 自动签发 Let's Encrypt 证书，省去证书维护 |
| 日志 | pino（结构化 JSON） | 单机场景容器日志 + 轮转即可 |
| 备份 | `pg_dump` 每日 + 上传目录 rsync 异地 | 单 VPS 没有冗余，备份是唯一的安全网 |

### 刻意不引入的东西

| 未引入 | 原因 | 何时再加 |
|---|---|---|
| Redis | 无会话共享、无缓存热点、无队列强需求 | 出现后台任务积压或接口变慢时 |
| 独立全文搜索引擎 | 三个模块的内容量级在十万行以内 | 检索出现相关性明显不足时 |
| 对象存储 | 图片为主，本地盘够用 | 上传目录超 20–50 GB，或开始存视频 |
| 消息队列 | 图片处理同步做完即可 | 视频转码 / 批量导入等长任务上线时 |
| Monorepo | 只有一个应用，拆包只增负担 | 出现第二个可独立部署的服务时 |
| Stripe 计费 | 当前无收费需求 | 明确要卖订阅时 |

## 4. 多账号隔离设计

这是本方案唯一有安全风险的部分，必须写死规则。

### 4.1 数据模型

```text
accounts          id / email / password_hash / slug / display_name / status / created_at
products          id / account_id / name / model_no / category / specs(jsonb) / is_public / sort
media_assets      id / account_id / product_id? / kind / path / width / height / variants(jsonb) / is_public
materials         id / account_id / product_id? / title / slug / content(html) / is_public / sort
```

约定：

- `account_id` 出现在**每一张业务表**上，即使可以通过 `product_id` 间接推导，也不省这一列——它让每个查询都能独立完成隔离，不必依赖 JOIN 链路。
- `is_public` 决定内容是否出现在 `/s/<slug>`，默认 `false`，必须显式勾选才对外。
- `slug` 全局唯一，生成时排除易混淆字符，且不可作为敏感信息（不能从 slug 反推账号邮箱）。

### 4.2 隔离执行策略

| 层 | 做法 |
|---|---|
| 数据访问 | 所有查询经统一 helper，强制注入 `account_id`；禁止在路由里直接 `db.select().from(products)` |
| 写入 | 服务端从会话取 `accountId` 覆盖请求体中的同名字段，**永不信任客户端传的 account_id** |
| 公开路由 | `/s/<slug>` 只走只读查询，额外强制 `is_public = true` |
| 双保险（可选） | 开启 Postgres RLS + 每请求 `set_config('app.account_id', …)`；一期可不上，但表结构已兼容 |
| 验证 | 为隔离逻辑写跨账号越权测试：用 A 账号的会话请求 B 账号的资源 ID，必须 404 而非 403（不泄露存在性） |

### 4.3 公开页设计

```text
/s/<slug>              账号主页：产品分类 + 产品卡片 + 资料入口
/s/<slug>/p/<model>    产品详情：参数表 + 媒体画廊 + 关联资料
/s/<slug>/m/<slug>     资料阅读页
```

- 全部 SSR，带 `og:image`（用 `next/og` 按产品图动态生成），客户分享到微信/Slack 时有预览图；
- 独立布局，与后台视觉解耦，不出现后台导航；
- 支持未公开内容返回 404，不出现"该内容未公开"这类提示；
- 预留子域名能力：路由层从 `slug` 解析，将来换成 `Host` 解析不需要改数据模型。

## 6. 部署拓扑

```text
                 ┌──────────── Caddy（自动 HTTPS）────────────┐
  Internet ──443──▶                                          │
                 └──┬──────────────────────────────┬──────────┘
                    │                              │
              ┌─────▼─────┐                  ┌─────▼─────┐
              │ Next.js   │──┬──────────────▶│PostgreSQL │
              │ (app)     │  │               └───────────┘
              └───────────┘  │               ┌───────────┐
                    │        └──────────────▶│ ./data    │
                    └── 只读挂载上传目录 ◀────│ (volume)  │
                                             └───────────┘
```

关键配置：

- Next.js 用 `output: 'standalone'` 产出精简镜像；
- 上传目录挂载为 volume，**不放在容器内**，否则重建即丢；
- 数据库不对公网暴露端口，仅容器网络内可达；
- 每日 `pg_dump` + `data/` 增量备份到 VPS 之外（对象存储或另一台机器），保留 7 天。

## 7. 分阶段计划

| 阶段 | 内容 | 验收标准 | 预估 |
|---|---|---|---|
| **P0 骨架** | 项目初始化、Docker Compose、DB 迁移、登录、管理员建号 | `docker compose up` 后能登录，账号隔离测试通过 | 1–2 天 |
| **P1 产品 + 媒体** | 产品 CRUD 与参数表、图片上传与多尺寸生成、素材画廊、排序 | 能录入一个真实产品并配好图 | 1 周 |

| **P3 打磨** | 全局搜索、3D/视频预览、导入导出、子域名 | 按实际使用反馈排序 | 按需 |

每个阶段结束都能部署出一版可用的系统，不做"三个月后一次交付"。

## 8. 风险与未决项

### 风险

| 风险 | 影响 | 应对 |
|---|---|---|
| **美国 VPS + 中国访问** | 后台传图、客户看展示页都可能明显变慢 | 前置 Cloudflare CDN（图片走缓存）；上线后实测延迟，必要时换香港/新加坡节点 |
| 本地磁盘容量 | 上传目录增长不可控，磁盘满会拖垮数据库 | 设定 20–50 GB 阈值，监控磁盘水位，到阈值切对象存储 |
| 单点故障 | 单 VPS 无冗余，宕机即全站不可用 | 每日备份 + 云厂商快照；不承诺高可用 |
| 隔离逻辑写漏 | 跨账号数据泄露是致命事故 | 统一 scoped helper + 强制越权测试进 CI |
| 一人一号模型限制 | 将来要支持团队协作需加组织层 | `accounts` 命名留出扩展空间，不叫 `users` |

### 未决项（需要你后续确认，不阻塞 P0）

1. **是否收费**：如果要卖订阅，需提前考虑 plan 与配额字段，越晚加越贵。
2. **域名**：`pmm.app` 是示例，实际域名待定，影响 Caddy 配置与 OG 图绝对地址。
3. **账号数量级**：几位、几十位还是上百位账号，决定是否需要分页与管理界面的复杂度。
4. **视频与 3D 的优先级**：P3 还是更晚，直接影响何时必须引入对象存储。
5. **内容语言**：中文为主、需要中英双语吗？双语会影响字段设计（是加 `_en` 列还是走翻译表）。
